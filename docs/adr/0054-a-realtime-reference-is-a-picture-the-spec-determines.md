# ADR-0054: Golden Images — A Realtime Reference Is A Picture The Specification Determines, Compared At Zero Tolerance

**Date**: 2026-09-12
**Status**: accepted
**Deciders**: Joshua Farr

## Context

[ADR-0007](0007-ci-rendering-tests.md) chose validation silence over pixels and deferred golden
images in its fifth alternative on one objection: a reference has to be generated by the same
rasterizer to be stable, which makes it useless as a check of hardware behaviour.
[ADR-0050](0050-a-frame-is-read-back-in-two-calls.md) supplied the readback and left the
objection standing, saying ADR-0007 holds until something blesses a reference.

Both devices the tree draws on are now real: this machine's Radeon, and the lavapipe the runner
was given. A picture blessed on either one and compared on the other is compared across two
conformant implementations, which is exactly the objection — unless the picture is one the
specification leaves them no room to disagree about. Rasterization of an axis aligned polygon on
integer boundaries under pixel centre sampling and the top-left rule is such a picture.
Blending, filtered sampling, multisample resolve and interpolation of a channel value that lands
near a rounding boundary are not: each is specified to a precision rather than to a value.

## Decision

A committed realtime reference may contain only what the Vulkan specification determines
pixel-for-pixel — axis aligned geometry on integer pixel boundaries, channel values of 0.0 or
1.0 or sampled unchanged from a texel, nearest filtering at one texel per pixel, no blending, no
multisampling — and is compared at a tolerance of zero. A case that wants anything else asserts
it by validation silence and spot checks, as ADR-0007 has it, and is not given a reference.

## Alternatives Considered

### Alternative 1: Restrict what a reference may contain, and compare exactly — **chosen**
- **Pros**: The file stops being one rasterizer's output and becomes the specification's, so the
  same bytes are owed by the driver an app ships against and by the software implementation CI
  draws with. A zero tolerance makes the restriction enforceable rather than aspirational: a
  case that drifts outside it fails on the device that was not used to bless it.
- **Cons**: Most of what a renderer does is outside the rule. Blending, text and filtering are
  the interesting half of a rendering change and none of them can be pinned this way.
- **Why not**: n/a — chosen.

### Alternative 2: One reference and a tuned tolerance
- **Pros**: Every case can have a picture, including the blended and filtered ones. This is what
  `moya` and `talyn` do, at a tolerance of 1.
- **Cons**: The offline renderers compare two runs of the same CPU code, where the tolerance
  absorbs float rounding across compilers. Here it would absorb the difference between two
  implementations, which is unbounded in principle and unknown in practice: a tolerance that
  passes today is a number nobody can derive, and the first genuine regression smaller than it
  is invisible.
- **Why not**: It answers ADR-0007's objection by hiding it. A test whose threshold is chosen to
  make it pass asserts the threshold.

### Alternative 3: A reference per implementation, selected by the device name
- **Pros**: Every case can be pinned exactly, on both devices, including blending and filtering.
- **Cons**: Two files per case, and a picture is only ever checked on the device that blessed
  it — a regression on a driver nobody committed a reference for passes. The set grows with
  every gpu the project is run on, and the first unrecognised device silently asserts nothing.
- **Why not**: It multiplies the artefact that is meant to be the single statement of what the
  renderer draws.

### Alternative 4: Bless on lavapipe and run only on lavapipe
- **Pros**: Stable by construction, and it is what ADR-0007 assumed a golden image would mean.
  CI is the only place the comparison would run, so a developer's gpu never fails a build.
- **Cons**: ADR-0007's own objection: it checks the API against a software implementation and
  says nothing about a driver. It also makes the suite two suites, since the cases that draw
  would assert different things locally and in CI.
- **Why not**: The point of pinning a picture is to catch what validation cannot see, on the
  thing that actually draws it.

## Consequences

### Positive
- A reference is portable evidence rather than a snapshot: it is blessed on one implementation
  and is a real assertion on every other.
- The renderers, and the upload path underneath them, gain coverage that a wrong colour, a wrong
  transform or a transposed texture fails — none of which validation can see and all of which
  reach the same five texels a spot check looks at.
- The rule is a test the case has to pass before it is written, so what a reference may contain
  is settled once rather than argued per case.

### Negative
- Blending, filtering, multisampling and text stay as uncovered as they are today, and the plan
  that builds on this says so rather than implying a later phase reaches them.
- A case is authored around what may be pinned — integer boundaries and full-range colours —
  which is not what the renderer is asked for anywhere else in the tree.
- Any picture is one more binary file per case in the repository, and a deliberate change to a
  renderer regenerates them.

### Risks
- **The rule may admit more than it should.** A picture can be spec-determined in theory and
  still differ, through a driver bug or a path the spec leaves looser than this reads it. That
  is what the plan's ordering is for: one probe picture goes through CI before any other is
  blessed. If it disagrees, the escape hatch is the case rather than the rule — the case drops
  its reference and keeps its spot checks, which is where every case starts today.
- **Regeneration is where a reference stops asserting anything**, because the cheapest response
  to a failure is to bless what was drawn. The mitigation is the same one the offline suites
  have: what was rendered is written to `data_out/` and the committed file is never touched by
  the test.
